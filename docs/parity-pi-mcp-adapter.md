# 与 `pi-mcp-adapter` 的功能对齐报告

**对照对象**：`pi-mcp-adapter` v2.33.0。
**方法**：逐文件阅读四个只读切片（代理面 / 生命周期与传输 / 协议与认证 / 配置缓存与界面），
每一条结论带 `file:line` 取证；本插件侧的缺陷都在真实 MCP 进程上端到端复现过。
pi 侧的数字来自其源码常数，不是 README 转述。

> pi 侧的 `file:line` 对应该版本，升级后需重新核对。本插件侧的引用只给文件路径。
>
> **贯穿全部改动的不变量**：模型可见的工具面始终保持 1525 字节 / 11 参数 / 381 token
> （`node scripts/measure-surface.mjs` 可复现）。下面提到的修复没有一项移动过它。

## 1. 结论

**核心机制一致，功能面差距很大。**

本插件声称「照 `pi-mcp-adapter` 做」的那部分——恒定代理工具 + 服务器懒启动 + 磁盘元数据缓存
——逐条核对后关键常数完全一致（§3）。在「省 token」这个它存在的理由上，本插件不落后，恒定面
约为 pi 的 45%（§8：`mcp` 之外 pi 还默认带一个 `mcpScript`）。

差距在「能连什么、能干什么」，且不是「少几个参数」的量级：

| 方向 | pi | 本插件 |
| --- | --- | --- |
| 认证 | OAuth 2.1 全流程（授权码 + PKCE、client_credentials、动态注册、发现、issuer 绑定）+ OS 钥匙串 + 跨进程刷新锁 | 无（只有静态 headers） |
| 协议能力 | elicitation、sampling、resources、prompts、progress、三种 `list_changed` 订阅、MCP Apps | 只有 tools（外加一种 `list_changed`） |
| 输出体量治理 | 截断 + 落盘、二进制资源落地、details 限幅、JSON Schema 方言校验 | 截断 + 落盘（其余无） |
| 配置与界面 | 6 个配置源 + 7 种宿主导入 + TUI 面板 + CLI + 10 个斜杠命令 | DSH 原生 config 单源 |

实测还查出 8 处行为差异，其中 3 处曾是本插件的真实缺陷（§5.1–§5.3，均已修）。

## 3. 逐条核对：核心机制一致

| 机制 | 结论 |
| --- | --- |
| 生命周期取值 | `keep-alive \| lazy \| lazy-keep-alive \| eager`，默认 `lazy` ✅ |
| 空闲回收默认 | 10 分钟，`0` 禁用 ✅ |
| 模式 → idle 覆盖 | 结果一致，机制不同：pi 靠「覆盖为 0 + 空闲扫描跳过独立的 keep-alive 集合」两条路；本插件没有那个集合，把 `keep-alive` 并进同一条规则（只有 `lazy` 继承全局窗口） |
| 激活时连接 | `keep-alive` 或 `eager` ✅ |
| 回收判定 | `connected && inFlight === 0 && now - lastUsedAt > timeout` ✅ |
| 扫描周期 | 30000 ms，`unref()` ✅ |
| 缓存文件 | 同构（pi 落在 agent 目录，本插件落在 `$DSH_HOME/storages/mcp-lazy/cache.json`） |
| 缓存版本 / TTL | `CACHE_VERSION = 1` / 7 天 ✅ |
| 缓存写入 | 临时文件 + `rename` 原子替换 ✅ |
| 搜索权重 | `{name:12, originalName:10, server:8, description:5, keywords:5}` 数值相同 ✅ |
| 词干最短长度 | 4 ✅ |
| 分页默认 | limit 12、offset 0 ✅ |
| `searchKeywords` | 只影响排序，不进 schema / 描述 / 缓存 ✅ |
| `directTools` | `boolean \| string[] \| "search"` ✅ |
| 全局 `directTools` | 插件级默认 + 每服务器覆盖（含 `false` 退出）✅ |
| `"search"` 语义 | 真 schema 但 inactive，搜索命中才激活 ✅ |
| `freezeDirectTools` | 首次同步后冻结提升，保 prompt 前缀 ✅ |
| 启动期零 I/O | 加载只读配置与缓存，不连接 ✅ |

## 4. 名义上有、行为不同

### 4.1 搜索排序（已对齐）

权重数值相同但算法原本不同（缺少整字段 / 前缀 / 子串的档位、覆盖率加成、命中门槛更严）。
现已按 pi 的结构重写：整字段命中 `×14`、前缀 `×9`、子串 `×6`，逐 token 精确 `×4`、词干 `×2`、
裸子串 `×1`，叠加覆盖率加成与「首 token 落在名称上」的加成；命中门槛改为「词组命中恒通过，
≤2 个 token 要求全覆盖，>2 个要求覆盖 ≥60%」。

保留了一处刻意的宽化：分词是 Unicode 感知的（`\p{L}\p{N}`），pi 只认 ASCII。所以非拉丁文字的
工具名在本插件里可搜，在 pi 里会被丢掉。

### 4.2 模式分派优先级

pi 是 `action > tool > connect > describe > instructions > search > server > status`；本插件是
`search > describe > instructions > connect > tool > status`。同时给 `search` 与 `tool` 时，
pi 调用工具，本插件搜索。

### 4.3 代理工具的描述

pi 的描述由 `buildProxyDescription(config)` 动态生成，会列出服务器名（含 search-mode 与 disabled
的）。本插件是常量字面量：模型不调 `mcp({})` 就不知道有哪些服务器。

两种取舍都成立——pi 认为「纯 config 函数、会话内稳定即可」，本插件要求「字节恒定、绝不触碰
KV 前缀」——但它是一个可观察的行为差异。

### 4.4 `search` 上限

pi 无上限；本插件裁剪到 40。这是刻意的安全加料，代价是模型无法一次列全上百个工具。

### 4.5 工具命名

pi 是 `{prefix}_{tool}`，`prefix ∈ server|none|short|mcp`，带内置名冲突跳过、跨服务器先到先得、
数量告警、UI 可见性过滤。本插件固定 `server__tool`（双下划线）——恒定带前缀，跨服务器与内置名
冲突不可能发生，所以那套机制在这里没有存在必要。缺的是前缀可配与可见性过滤。

### 4.6 环境变量

pi 的 `inheritEnv` 默认 true，整份拷贝 `process.env`，没有黑名单。本插件默认**洗掉**
`/KEY|PASSWORD|SECRET|TOKEN/i` 与 `DSH_*`。安全上更严，但这是个**迁移陷阱**：一个在 pi 下依赖
环境里 `GITHUB_TOKEN` 的服务器，搬过来会静默起不来，除非显式写 `env` 或用 `envFrom` 取。

## 5. 实测差异

### 5.1 已修 — 放宽 `includeTools` / `excludeTools` 永不生效

端到端复现（真实 MCP 进程，7 个工具）：缓存里存的是**过滤后**的集合（`echo` 不在其中），而
`computeConfigHash` **排除**了这两个字段，于是删掉一条 `excludeTools` 后哈希不变、条目仍被判为
有效，读路径再过滤一次对已过滤集合是幂等的——被排除的工具找不回来，最长 7 天。

症状是「只能变严不能变松」。pi 两侧都做对了：缓存存原始集合，过滤在重建时应用，且这两个字段
算进哈希。

**修法**：过滤从写入路径整体移到读取路径。没有改哈希，因为过滤是廉价的读取期操作，不该有
「改一次过滤条件就作废整份目录」的权力——但两个前提必须同时为真，代码注释里写明了这一点。

### 5.2 已修 — 驼峰工具名无法子词搜索

`normalizeSearchText` 原本不拆驼峰（pi 有）。对工具名 `getPixels`、描述用中性文字：

| 查询 | 修复前 | 修复后 |
| --- | --- | --- |
| `pixels` | 0 命中 | 命中 |
| `get pixels` | 0 命中 | 命中 |
| `getPixels` | 1 命中 | 命中 |

补一句为什么第一次没发现：先前测的是描述里带 "pixel data" 的工具，`pixels` 命中的是**描述**
里的词干，把名字里的缺陷盖住了。换成中性描述才复现。影响面不小——大量 MCP 服务器用驼峰工具名。

### 5.3 已修 — 正则搜索没有安全闸

pi 用 `recheck` 做 ReDoS 分析，不安全就返回 `unsafe_pattern`，另有 256 字符查询上限。
本插件原本直接 `new RegExp(pattern, 'i')`。实测回溯爆炸（`(a+)+c` 对失败串）：

| 重复字符数 | 耗时 |
| --- | --- |
| 16 | 4 ms |
| 20 | 8 ms |
| 24 | 131 ms |
| 28 | **2078 ms** |

指数增长，36 个字符约 8 分钟。而且搜索是**同步**跑在工具调用里的，会阻塞事件循环——不只是慢，
是整个会话卡住。

**修法**：三层拒绝，都以值返回而不是抛出——超过 256 字符、结构上嵌套了无界量词、语法非法。
嵌套量词检测是一次保守的结构扫描（跟踪分组深度与「该分组内是否含无界量词」）。这里有个必须
说清的取舍：pi 用的是一个**额外依赖**，本插件保持依赖精简，换来的只是**更窄的保证**——重叠
选择分支 `(a|aa)+` 与多项式级的 `a*a*a*b` 不在此检查范围内，代码注释里明说了这一点。

顺带修掉一个 UX 缺陷：正则被拒时原本显示「没有匹配」，模型会据此认定工具不存在，而不是自己的
模式写错了。现在拒绝原因原样展示。

### 5.4 已补 — 没有失败退避

pi 有 60 秒适配器级抑制（keep-alive 另有指数退避）。本插件原本没有：坏掉的服务器**每次调用都
重新 spawn 并等满超时**。现在同样是 60 秒抑制，状态里带上「多久前失败、还剩多久」，且显式
`connect` 绕过。

### 5.5 已补 — 没有 stderr 捕获

pi 保留子进程 stderr 的最后 3 行 / 8 KiB 并附到连接错误里。本插件原本没有，启动失败只看得到
SDK 的报错。现在默认捕获并保留有界尾巴，`debug: true` 恢复 `inherit`。

### 5.6 部分处理 — 冷缓存不自愈，也不预热

pi 有两条自愈路径：缓存文件缺失时首启连接所有启用的服务器；启用了 `directTools` 但缓存失效的
服务器启动时自动连接修复。本插件**从不自动连接**（这是加载期零进程的根基），代价是真实的：
新加一个服务器后 `mcp({ search })` 只会说「还没有缓存」，模型必须先想到调 `connect`。

本插件的处理方式是把「模型缺一个动作」变成「状态里明写那个动作」：`mcp({})` 点名无缓存的服务器
并给出连接动作，代价是零进程、零 I/O。禁用服务器不会被点名。

### 5.7 未改 — 刷新语义更弱

pi 订阅 tools / prompts / resources 三种 `list_changed` 并重建对应目录。本插件只处理工具列表
——在它支持的范围内够用，没有 prompts / resources 可言。等做那两项时一起补才合理。

### 5.8 附带发现 — 正则命中排序

pi 的正则命中得分为 0 且不重排（保持元数据顺序）；本插件按名称重排。本插件的顺序是确定性的、
不依赖 Map 迭代次序，保留。

## 6. pi 有而本插件没有

按重要性排列。

### 6.1 认证（整块缺失）

OAuth 授权码 + PKCE、`client_credentials`、动态客户端注册、PRM 发现、issuer 绑定校验、`state`、
headless 回退；bearer token 及其插值与命令间接引用；凭据存 **OS 钥匙串**（无明文回退）；
**跨进程刷新锁**；自定义 header、每请求 header 命令、自定义 CA。

### 6.2 协议能力

| 能力 | pi | 本插件 |
| --- | --- | --- |
| `tools` | ✅ | ✅ |
| `resources` | ✅ 伪工具 `read_<name>`，可关 | ❌ |
| `prompts` | ✅ 注册成斜杠命令，缓存内零连接注册 | ❌ |
| `elicitation` | ✅ 表单模式全流程 + URL 模式 | ❌ |
| `sampling` | ✅ 模型选择、两次交互确认 | ❌ |
| `progress` | ✅ 桥接到 UI 通知 | ❌ |
| `roots` / `completions` / `logging` | ❌（pi 也没做） | ❌ |

### 6.3 已补 — 输出体量治理

pi 的守卫：文本超 50 KiB / 2000 行截断、全文落盘并给出路径；图片块原样透传；结构化内容限幅；
二进制资源落地为文件，base64 永不进上下文。

本插件原本**没有任何截断**。这里有一条值得记下的错误认识：框架层**不会**替工具兜住超大输出。
`spill` 只出现在单个工具各自的实现里，`dsh-tools` 与 `dsh-agent-loop` 都没有对工具返回值的截断
机制——所以工具不自己截，就全额进上下文。这一条对「省 token」的目标伤害最大：插件省下的是工具
定义那几百 token，一次无上限返回可以一口吃掉几万。现在已有 `outputGuard`，设计取舍见
[design.md](design.md) 的 D6。

### 6.4 其它缺失

沙箱脚本批量调用（见 §7.2）、URL 安装、按服务器列工具、工具审批门、MCP Apps、协议时代协商、
`npx` 父进程消除、trace、状态事件通道、端点探测、配置互操作（6 个配置源 + 7 种宿主导入）、TUI
面板与斜杠命令全家桶、SSE 与 unix socket 传输、JSON Schema 方言校验。

## 7. 本插件有而 pi 没有，或本插件更好

### 7.1 恒定面更小

见 §8。

### 7.2 `mcpScript` 在 DSH 上有平台级等价物

pi 的 `mcpScript` 让模型用一个工具调用批量跑 MCP 调用。**DSH 原生有 `run_code`（PTC 模式）**：
程序通过嵌套执行调用注册表里对 agent 可见的工具，只有外层结果进模型历史——也就是说，在 PTC
呈现模式下模型本来就能写一段程序多次调用 `mcp({ tool })`，那正是 `mcpScript` 的能力，不需要在
插件里再实现一个沙箱。

两点保留：(a) 呈现模式是整体二选一，不是额外挂一个工具；(b) PTC 模式下原生工具 schema 不进请求，
本插件的代理工具也就不会出现在请求里，token 账完全变了。

### 7.3 默认洗环境变量

见 §4.6。更安全，但迁移时要留意。

### 7.4 服务器名校验在加载期

本插件在 `apply()` 就拒绝 stdio 缺 command、http 缺 url、`serverName` 重复，错误出现在配置所在的
时刻；pi 是连接时才检查「必须恰好配置 command / url / socket 之一」，且几乎不校验 `serverName`。

### 7.5 依赖更少

运行时 2 个依赖，pi 17 个（含原生模块）。

## 8. token 账

两边同一口径：字符数 ÷ 4（估算，对 JSON 密集文本会低估，所以只用于两边对比，不用作绝对值）。

| | pi | 本插件 |
| --- | --- | --- |
| 模型可见工具数 | 2（`mcp` + `mcpScript`）+ 可选提升的工具 | 1（`mcp`） |
| `mcp` 描述（渲染后） | 1409 字符（0 服务器）/ 1448（3 个）/ 1519（10 个）≈ 352–380 token | 297 字符 ≈ 74 token |
| `mcp` 参数描述 | 14 个参数、合计 825 字符 ≈ 206 token | — |
| `mcpScript` 描述 | 804 字符 ≈ 201 token | 不存在 |
| **整个工具定义** | 约 600 token；加 `mcpScript` 约 850 | **1525 字节 ≈ 381 token**（脚本实测，含全部结构） |

本插件的恒定面约为 pi 的 **45%**，而且省下来不是靠砍功能描述——描述只占 74 token，其余是参数
结构。顺带一个事实修正：pi 的 README 写 "One proxy tool (~200 tokens)"，但它 `mcp` 工具的描述
文字本身渲染出来就有 1409 字符 ≈ 352 token，那个数字已经过时。

反向的账：pi 有输出守卫（防一次返回吃掉几万 token）、`npx` 父进程消除、缓存载荷精简、
`directTools: "search"` 保持工具 inactive。本插件这四项里现在有第一项。所以「谁更省」取决于
用法：工具多、调用少的场景本插件赢；有服务器会吐大结果的场景 pi 赢很多。

| 3 | 正则安全闸（§5.3） | 长度上限 + 嵌套无界量词检测；拒绝原因贯穿到模型 |
| 4 | 输出体量治理（§6.3） | 新增 `src/output-guard.ts` |
| 5 | 失败退避 + stderr 尾巴（§5.4、§5.5） | 60 秒抑制（显式 connect 绕过）；stderr 尾巴；`debug` 开关 |

修复过程中靠测试才暴露出来的一条：SDK 默认让 stdio 的 stderr 走 `inherit`，`transport.stderr`
因此是 `null`——启动失败时**根本拿不到**诊断。这也说明捕获必须是默认行为，因为启动失败才是最
常见的场景，而那个尾巴是唯一能解释它的东西。
